一、Web基础§

1.1 Web的工作原理§

Web是一个由大量互联网页和资源组成的系统，通过互联网将信息传递给用户。其工作原理可以简化为以下几个步骤：

  1. 用户请求：用户通过浏览器输入URL或点击链接发起请求。
  2. DNS解析：浏览器通过DNS服务器将域名解析为IP地址。
  3. 建立连接：浏览器与服务器建立TCP连接，通常使用80端口（HTTP）或443端口（HTTPS）。
  4. 发送请求：浏览器向服务器发送HTTP请求报文。
  5. 服务器响应：服务器处理请求并返回HTTP响应报文。
  6. 渲染页面：浏览器解析响应内容并渲染网页。

二、HTTP协议§

HTTP（Hypertext Transfer Protocol，超文本传输协议）是一种用于在网络上进行数据交换的协议，是web的基础之一。它通过请求-响应的方式，在客户端和服务器之间传输数据，是互联网上最常用的协议之一，定义了客户端与服务器之间的请求和响应格式。

HTTP 使用标准的ASCII码进行通信，是一种无状态的协议，即每个请求都是相互独立的，服务器不会记录之前的状态。

🔒注：

① 关于 ASCII：起始行和头部字段确实是 ASCII 文本，但请求体/响应体可以是任意二进制（图片、压缩包都是二进制）。正因为 body 能放二进制，才有了后面的 multipart 这种传法。

② 关于无状态：服务器不记事 → 每次请求都得由客户端自己带上"我是谁"的凭证 → 而客户端带来的东西是可以被伪造的。这就是身份认证类漏洞的根源。

2.1 HTTP的版本§

  • HTTP/1.0：早期版本，每次请求都需要建立新的TCP连接。
  • HTTP/1.1：改进版本，支持持久连接（Keep-Alive）、管线化（Pipelining）等特性。
  • HTTP/2：进一步优化，支持多路复用、头部压缩和服务器推送。
  • HTTP/3：基于QUIC协议，提供更快的连接建立和更低的延迟。

2.2 HTTP 的请求-响应§

HTTP 的基本工作原理是客户端（通常是 web 浏览器）向服务器发送请求，服务器接收到请求后，返回相应的资源。这些资源可以是网页、图像、音频文件、视频等。

HTTP 使用了客户端-服务器模型，其中客户端发送请求，服务器返回响应。

HTTP 的请求-响应模型通常由以下几个步骤组成：

  1. 建立连接：客户端与服务器之间建立连接。

  2. 发送请求：客户端向服务器发送请求，请求中包含要访问的资源的 URL、请求方法、请求头以及可选的请求体。

  3. 处理请求：服务器接收到请求后，根据请求中的信息找到相应的资源，执行相应的处理操作。

  4. 发送响应：服务器将处理后的结果封装在响应中，并将其发送回客户端。

  5. 关闭连接：在完成请求-响应周期后，客户端和服务器之间的连接可以被关闭，除非使用了持久连接（如 HTTP/1.1 中的 keep-alive）。

2.3 HTTP请求报文§

HTTP请求报文由以下部分组成：

http
//1.请求行：包括请求方法（如GET、POST）、请求URI和HTTP版本。
GET /index.html HTTP/1.1    
//2.请求头部：包含请求的元数据，如主机（Host）、用户代理（User-Agent）、接受的内容类型（Accept）等。
Host: www.example.com
User-Agent: Mozilla/5.0
Accept: text/html
​//3.空行：用于分隔头部和消息体。

//4.消息体：可选部分，包含请求的实际数据，如POST请求的数据。
（body）

🔒请求头都可以改

请求头 改了有什么用
Host 影响服务器认为你在访问哪个站点
User-Agent 有些程序会把它写进日志或直接用到（所以它可能是个注入点）
Referer 有些站只用它判断"你是不是从本站来的"，改掉就能绕过
Cookie 身份凭证，伪造/修改的常见位置
Content-Type 决定后端怎么解析你的 body
X-Forwarded-For 表示"客户端真实 IP"，很多代码直接读它判断是不是内网，但它由客户端随意填写

通用规律：凡是客户端能自己填的，服务端都不该无条件相信，相信了就可能存在漏洞。

2.4 HTTP响应报文§

HTTP响应报文由以下部分组成：

http
//1.状态行：包括HTTP版本、状态码和状态短语。
HTTP/1.1 200 OK
​//2.响应头部：包含响应的元数据，如内容类型（Content-Type）、内容长度（Content-Length）、服务器信息（Server）等。
Date: Wed, 18 Apr 2024 12:00:00 GMT
Server: Apache/2.4.1 (Unix)
Last-Modified: Wed, 18 Apr 2024 11:00:00 GMT
Content-Length: 12345
Content-Type: text/html; charset=UTF-8
​//3.空行：用于分隔头部和消息体。

//4.消息体：包含实际的响应数据
<!DOCTYPE html>
<html>
<head>
    <title>Example Page</title>
</head>
<body>
    <h1>Hello, World!</h1>
    <!-- The rest of the HTML content -->
</body>
</html>
响应头信息 描述
Server / X-Powered-By 技术栈和版本。比如 X-Powered-By: PHP/5.6.40，你就知道这是老版本 PHP，某些老特性可能还能用
Content-Type 响应体的媒体类型（MIME类型），如text/html; charset=UTF-8, application/json等。
Set-Cookie 设置客户端的 cookie。看 Cookie 有没有 HttpOnly、Secure 这类属性
Location 重定向到哪去了 —— 有时会暴露出隐藏的路径或参数
X-Powered-By 这种头在真实环境里通常建议关掉（等于白送情报），靶场里则经常故意留着。

2.5 HTTP状态码§

  • 1xx：信息响应，表示接收的请求正在处理，如100 Continue（客户端应继续其请求）。
  • 2xx：成功响应，表示请求正常处理完毕，如200 OK、201 Created。
  • 3xx：重定向响应，需要后续操作才能完成这一请求，如301 Moved Permanently、302 Found。
  • 4xx：客户端错误，表示请求包含语法错误或无法完成，如400 Bad Request、404 Not Found。
  • 5xx：服务器错误，表示服务器在处理请求的过程中发生了错误，如500 Internal Server Error、502 Bad Gateway。

🔒 几个状态码在实战里的含义

状态码 实战含义
200 正常。但扫目录时要注意"假 200"——有些站对不存在的路径也返回 200，只是内容是个统一错误页，得靠响应长度去区分
301 扫目录时出现 301，通常说明这个目录真实存在
302 响应体里可能藏东西，而且浏览器会自动跟着跳走，你就看不到中间那一步了
403 路径存在但被拒绝访问。和 404（不存在）是两回事，403 说明"这里确实有东西"
405 方法不允许 —— 等于告诉你这个路径支持哪些方法
500 服务端出错。报错信息经常泄露路径、SQL 语句、框架版本
502 / 504 网关错误 / 超时。探测内网服务时常用来判断"这里有没有东西在响应"

重点："拦截 302 看响应体"

浏览器和很多工具默认自动跟随重定向，于是你只看到最终页面，中间那一跳的信息全丢了。用 Burp 抓包时不自动跳转，就能看到：

  1. Location 头指向哪里（暴露隐藏路径）
  2. 302 的响应体里有没有提示文字或数据（规范并没有禁止 302 带 body）
  3. 要不要手动决定跟不跟

操作：Burp 的 Repeater 默认就不跟随，直接看第一个响应；curl 则要故意不加 -L。

2.6 HTTP方法§

HTTP 方法指定了客户端可以对服务器上的资源执行哪些动作。

  • GET：请求从服务器获取指定资源。这是最常用的方法，用于访问页面。
  • POST：请求服务器接受并处理请求体中的数据，通常用于表单提交。
  • PUT：请求服务器存储一个资源，并用请求体中的内容替换目标资源的所有内容（更新指定资源）。
  • DELETE：请求服务器删除指定的资源。
  • HEAD：与 GET 类似，但不获取资源的内容，只获取响应头信息。
  • OPTIONS：查询服务器支持的HTTP方法。
  • PATCH：对资源进行部分修改。与 PUT 类似，但 PATCH 只更改部分数据而不是替换整个资源。

🔒 ：

  • GET 的参数在 URL 里 → 会进服务器日志、会留在浏览器历史里。

  • POST 的参数在 body 里 → 但要注意 body 的格式由 Content-Type 决定。

  • OPTIONS 会返回一个 Allow 头，直接列出这个路径支持哪些方法，是免费的情报。 习惯：拿到一个接口后，把几种方法都试一遍。因为不同方法有时会走不同的处理逻辑，可能某个方法少做了检查。

2.7 HTTP content-type§

Content-Type（内容类型），一般是指网页中存在的 Content-Type，用于定义网络文件的类型和网页的编码，决定浏览器将以什么形式、什么编码读取这个文件，这就是经常看到一些 PHP 网页点击的结果却是下载一个文件或一张图片的原因。

Content-Type 标头告诉客户端实际返回的内容的内容类型。

语法格式：

http
Content-Type: text/html; charset=utf-8
Content-Type: multipart/form-data; boundary=something

常见的媒体格式类型如下：

  • text/html ： HTML格式
  • text/plain ：纯文本格式
  • text/xml ： XML格式
  • image/gif ：gif图片格式
  • image/jpeg ：jpg图片格式
  • image/png：png图片格式

以application开头的媒体格式类型：

  • application/xhtml+xml ：XHTML格式
  • application/xml： XML数据格式
  • application/octet-stream ： 二进制流数据（如常见的文件下载）
  • application/x-www-form-urlencoded ： <form encType=""> 中默认的 encType，form表单数据被编码为key/value格式发送到服务器（表单默认的提交数据的格式）

另外一种常见的媒体格式是上传文件之时使用的：

  • multipart/form-data ： 需要在表单中进行文件上传时，就需要使用该格式

🔒 ：

① 为什么发 POST 一定要带 Content-Type？

因为它决定后端用哪个解析器处理你的 body。

拿 PHP 举例：$_POST 这个变量只在 Content-Type 是 application/x-www-form-urlencoded 或 multipart/form-data 的时候才会被填充。如果你发的是 application/json，PHP 不会去解析 body，$_POST 是空的。

结论：

  • 源码里写的是 $_POST['x']，那你就必须用 POST + 表单格式发，缺一不可。
  • 遇到"参数明明传了却读不到"，第一件事就是检查 Content-Type 和请求方法。

② Content-Type 只是客户端的一个声明，它不校验文件内容，改起来毫无成本。 所以任何"靠 Content-Type 判断文件类型"的校验，都是可以绕过的。

2.8 MIME 类型§

MIME (Multipurpose Internet Mail Extensions) 是描述消息内容类型的标准，用来表示文档、文件或字节流的性质和格式。

MIME 消息能包含文本、图像、音频、视频以及其他应用程序专用的数据。

浏览器通常使用 MIME 类型（而不是文件扩展名）来确定如何处理URL，因此 Web 服务器在响应头中添加正确的 MIME 类型非常重要。如果配置不正确，浏览器可能会无法解析文件内容，网站将无法正常工作，并且下载的文件也会被错误处理。

MIME 类型通用结构：

text
type/subtype

MIME 的组成结构非常简单，由类型与子类型两个字符串中间用 / 分隔而组成，不允许有空格。type 表示可以被分多个子类的独立类别，subtype 表示细分后的每个类型。

MIME类型对大小写不敏感，但是传统写法都是小写。

两种主要的 MIME 类型在默认类型中扮演了重要的角色：

  • text/plain 表示文本文件的默认值。
  • application/octet-stream 表示所有其他情况的默认值。

🔒 请求里的 Content-Type 和响应里的 Content-Type 不是一回事

方向 含义 是否可信
请求里的 Content-Type 客户端说"我传的是什么" ❌ 完全不可信，客户端随便写
响应里的 Content-Type 服务器说"我返回的是什么" ✅ 服务器定的，浏览器据此决定怎么渲染
  • 请求方向：如果服务端拿到上传文件的 Content-Type 就判断"这是图片，放行"，那你把 .php 文件的 Content-Type 改成 image/png 就绕过了。
  • 响应方向：如果站点把你上传的内容（比如一张图）以 text/html 返回，浏览器会把它当网页渲染，里面的脚本就可能执行。

2.9 HTTPS§

HTTP 本身是不安全的，因为传输的数据未经加密，可能会被窃听或篡改。

HTTPS（Hypertext Transfer Protocol Secure）是在HTTP基础上增加了SSL/TLS加密，确保数据在客户端和服务器之间传输的安全性。

🔒 HTTPS 管什么、不管什么

  • 管：传输过程中别人看不到、改不了，也能确认你连的是真的那个站。
  • 不管：SQL 注入、文件上传、越权这些应用层的问题。因为攻击者可以直接用自己的浏览器正常访问，加密对他没有任何阻碍。

另外，刷靶场时经常要"忽略证书错误"（curl 加 -k、蚁剑勾选忽略），那只是为了方便连自签证书的靶机。真实环境里忽略证书等于把加密废掉。

2.10 Cookie 与 Session§

前面说过 HTTP 是无状态的——服务器不记得你上一次请求是谁。但实际用网站时明显"记得"你登录过，靠的就是 Cookie 和 Session。

  • Cookie：存在客户端（浏览器）里的一小段数据。
  • Session：存在服务器端的数据，客户端只拿到一个编号。

Cookie 是什么§

http
# 服务器下发
Set-Cookie: PHPSESSID=abc123; Path=/; HttpOnly

# 浏览器之后每次都自动带上
Cookie: PHPSESSID=abc123

两个特点：

  • 浏览器会自动携带 —— 你不需要手动做什么，它自己就带上了。这点很重要，因为跨站请求也会带上（CSRF 的根源）。
  • 它存在客户端，所以用户可以看见、也可以改 —— F12 → Application → Cookies 里能直接看到并编辑。

但注意：只要服务端设计是对的，改了也没用。

Session 与 PHPSESSID§

Session 是为了解决"不想把敏感数据放在客户端"而出现的。

工作流程：

text
① 你登录成功
② 服务器创建一个 Session（在服务器上存一份数据，比如 $_SESSION['user'] = 'admin'）
③ 服务器生成一个随机编号（Session ID），通过 Set-Cookie 发给你
④ 之后你的每个请求都自动带上这个编号
⑤ 服务器拿这个编号去查自己存的那份数据 → 知道你是谁

关键点：真正决定"你是谁"的那份数据在服务器上，客户端手里只有一个编号。

PHPSESSID 是 PHP 默认的 Session ID 名字。所以：

  • 见到 PHPSESSID 就能确定是 PHP 站点
  • PHP 默认把 Session 数据存在服务器上的 sess_<SessionID> 文件里（通常在 /tmp 目录）

🔒 ：Session 数据存在服务器上的文件里，所以如果有"文件包含"漏洞，就可能通过包含 sess_<你的SessionID> 文件来执行内容 —— 这就是 Session 文件包含。

Cookie 的关键属性§

Set-Cookie 后面可以跟一串属性，每个属性都有安全含义。

属性 作用 配错的后果
Domain 允许哪些域携带这个 Cookie 设得太宽 → 子域也能读到 → 子域被攻破就会话泄露
Path 允许哪些路径携带 设得太宽 → 同站其他应用也能看到
Expires / Max-Age 有效期 太长 → 被盗后能用很久；不设（会话 Cookie）→ 关浏览器就失效
HttpOnly 禁止 JS 读取（document.cookie 拿不到） 缺失 → XSS 可以直接偷走 Cookie
Secure 只在 HTTPS 下发送 缺失 → 可能被降级到 HTTP，明文泄露
SameSite 跨站请求时是否携带 缺失 → CSRF 防护失效（现代浏览器默认 Lax）

其中 HttpOnly 需要注意：

说明
✅ 能防 JS 读取 Cookie（document.cookie 拿不到它）→ 防住了"XSS 偷 Cookie"
❌ 不能防 浏览器自动携带 Cookie 的行为 → 所以完全防不住 CSRF

原因是 HttpOnly 管的是"读取"，不管"发送"。而 CSRF 攻击根本不需要读到 Cookie，它只需要让你浏览器自动带着 Cookie 去发一个请求就行了。

Cookie、Session、Token 的差异§

Cookie Session Token（如 JWT）
数据存在哪 客户端 服务器 客户端（自己带着）
客户端拿到什么 数据本身 只是一个编号（Session ID） 数据本身 + 签名
服务器要不要存 不存 要存（占内存/存储） 不存（无状态）
客户端能改吗 能改 编号能改，但改了查不到对应数据 能改，但签名会失效
典型形式 PHPSESSID=xxx PHPSESSID=xxx Authorization: Bearer eyJ...

注意：Cookie 和 Session 不是对立关系——Session 通常就是靠 Cookie 来传那个编号的。所以 "Cookie" 讲的是怎么传，"Session / Token" 讲的是存什么。

为什么 Cookie: user=1 能骗过后端？§

这是理解认证漏洞最关键的一问。

根本原因：后端代码把 Cookie 里的值直接当成了可信数据来用。

php
// 有漏洞的写法（大致意思）
$user = $_COOKIE['user'];        // 直接读 Cookie
if ($user == 1) {                // 直接拿它判断身份
    echo $flag;                  // 于是改 Cookie 就拿到了
}

程序在这个 Cookie 值上做了某种判断（比如拿它和某个数字、某个字符串比较），那你只要顺着它的比较逻辑改这个值，就能通过。

对比安全的写法：

php
// 安全的写法
$sid = $_COOKIE['PHPSESSID'];    // 只从 Cookie 拿编号
// 拿编号去服务器端查真正的身份，客户端改不了这份数据
session_start();
if ($_SESSION['is_admin'] === true) { ... }

区别在于：

身份信息从哪来 客户端能改吗
有漏洞 直接从 Cookie 读 ✅ 能改 → 能伪装
安全 Cookie 只给编号，真正的身份在服务端 ❌ 改编号也没用（查不到）

所以"改 Cookie 提权"的本质是：不是 Cookie 不安全，而是程序把"客户端说的"当成了"事实"。

任何完全由客户端决定的身份信息，都等于没有校验。

再往下推一步：如果客户端带来的东西带了签名（服务端用密钥签过），客户端就改不了了——这就是 Token 的设计思路。但如果密钥泄露或签名算法有缺陷，又会回到同样的问题。

认证的核心不是"客户端带来了什么"，而是"服务端能不能验证它没被改过"。

2.11 multipart/form-data§

它和 application/x-www-form-urlencoded 的区别：

对比项 application/x-www-form-urlencoded multipart/form-data
结构 一个字符串：k1=v1&k2=v2 一个容器：用 boundary 切出很多段
每个字段 只有名字和值 每段有自己的头部（Content-Disposition、Content-Type）
传二进制 ❌ 要百分号编码，易损坏 ✅ 直接按原始字节传
传文件 ❌ 无法表达"文件名" ✅ filename="x.png"
非 ASCII ❌ 只保证 ASCII ✅ 配合 charset 或 filename*

报文长这样：

http
POST /upload HTTP/1.1
Host: target.com
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Length: 219

------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="username"

admin
------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="avatar"; filename="a.png"
Content-Type: image/png

（文件的原始二进制内容）
------WebKitFormBoundary7MA4YWxkTrZu0gW--

结构要点：

  1. 第一行的 boundary=xxx 定义分隔符，由客户端生成，服务端只是照着切。
  2. 每一段开头是 -- + boundary。
  3. 每段头部至少有 Content-Disposition: form-data; name="字段名"；文件段还多一个 filename="..."。
  4. 文件段还有自己的 Content-Type ← 注意这里有两个 Content-Type。
  5. 每段头部之后是一个空行，然后是该段的原始数据。
  6. 结束标志：-- + boundary + --（末尾多两个短横线）。

🔒 两个 Content-Type

text
第 1 个（请求头，外层）： Content-Type: multipart/form-data; boundary=xxx
                       → 说明"整个 body 是 multipart 格式"

第 2 个（文件段内层）： Content-Type: image/png
                       → 说明"这一段里的文件是 PNG"

它们是两个独立的东西，可以不一致。 这就是"只校验 Content-Type"好绕的原因：

  • 你上传一个 .php 文件，但只在段内写 Content-Type: image/png → 校验通过
  • 后端真正保存时用的是 filename 里的扩展名 → 拿到 .php 文件

测试时的做法：分别改外层和内层这两个位置，看哪一次被拦 —— 这就是在定位它到底校验了哪个。

其他和上传相关的细节：

细节 说明
filename 后端常用它决定保存的文件名/扩展名 → 后缀绕过的入口
name 决定后端收到的字段名

用 curl 发 multipart 请求：

bash
# 1. 最基本：-F 会自动按 multipart 发送
curl -X POST http://target.com/upload -F "avatar=@/path/a.png"

# 2. 手工指定该段的 Content-Type —— 上传题绕过的标准动作
curl -X POST http://target.com/upload \
     -F "avatar=@shell.php;type=image/png" \
     -F "username=admin"

# 3. 指定 filename（决定服务端拿到的文件名）
curl -X POST http://target.com/upload \
     -F 'avatar=@shell.php;filename=shell.png;type=image/png'

# 4. 带 Cookie、走 Burp 代理、忽略证书、显示详细过程
curl -X POST http://target.com/upload \
     -b "PHPSESSID=abc123" \
     -x http://127.0.0.1:8080 -k -v \
     -F "avatar=@shell.php;type=image/png;filename=shell.png"

常用参数：-F（表单字段/文件）、-b（Cookie）、-H（自定义头）、-x（代理）、-k（忽略证书）、-v（看完整报文）、-L（跟随重定向，调试 302 时故意不加）。

三、URL§

统一资源定位符，用于标识互联网上的资源。它一般由协议类型（如http/https）、地址、端口号、路径、查询参数和fragment组成。

例如：https://www.example.com:8080/app/user/info.do?param1=value1&param2=value2 #abc

3.1 地址§

地址部分用来确定URL所要访问的服务器的网络地址（也就是网址）。在URL中，地址可以用三个形式来表示：域名、主机名、IP地址

  1. 域名：我们平时输入的www.baidu.com、www.qq.com就是域名，计算机和路由器并不能直接认出域名，还需要通过DNS服务器找到域名对应的IP地址，再通过底层的TCP/IP协议路由到对应的机器上去（具体可以去学习计算机网络的相关内容）

  2. 主机名：就是某台计算机的名字，在一个局域网内，可以通过主机名找到要访问的计算机。主机名和域名一样，计算机和路由器不认它，需要通过HOSTS文件这样的技术找到主机名和IP地址的关联关系，最后还是翻译成IP地址再继续发送网络请求 localhost就是一种比较特殊的主机名，是给 回环地址的一个标准主机名，就是代表本机自己的地址。

  3. IP地址：在URL中也可以直接用IP地址，如192.168.0.1

3.2 端口号§

一台服务器上可以开多个端口号，往往一个网络服务程序就对应一个端口号。

比如，我在机器 A 上，开了两个服务程序，分别是 Tomcat和SSH，让它们分别关联端口8080和22，那URL中如果端口号是8080就是会访问到Tomcat程序，22就会连接SSH服务。

http协议默认端口号为80。

3.3 fragment§

主要资源是由 URI 进行标识，URI 中的 fragment 用来标识次级资源。fragment 对于 HTML 文档来说就是页面内的定位标识符，可以实现 HTML 页面内的定位。

在 URI 的末尾通过 hash mark（#）作为 fragment 的开头，其中 # 不属于 fragment 的值。

  • # 有别于 ?，? 后面的查询字符串会被网络请求带上服务器，而 fragment 不会被发送的服务器；
  • fragment 的改变不会触发浏览器刷新页面，但是会生成浏览历史；
  • fragment 会被浏览器根据文件媒体类型（MIME type）进行对应的处理；
  • Google 的搜索引擎会忽略 # 及其后面的字符串。

🔒 因为 # 之后的内容根本不发给服务器

所以：如果在 payload 里直接写 #，它后面的所有内容都会被浏览器丢掉，等于没发。

如果需要 # 这个字符本身，必须写成 %23。

3.4 URL 编码规则§

URL 中规定了一些具有特殊意义的字符，常被用来分隔两个不同的 URL 组件，这些字符被称为保留字符。例如：

  • :：用于分隔协议和主机组件。

  • /：用于分隔主机和路径。

  • ?：用于分隔路径和查询参数等。

  • =：用于表示查询参数中的键值对。

  • &：用于分隔查询多个键值对。

  • 其他：. ... # @ $ + ; %

编码原因：URL 中的某些字符会引起歧义，而且URL 的编码格式采用的是 ASCII 码而非 Unicode 格式，这表明 URL 中不允许包含任何非 ASCII 字符（比如中文），否则就会造成 URL 解析错误。

编码规定：

URL 中只允许使用 ASCII 字符集可以显示的字符，比如英文字母、数字、和- _ . ~这些不需要编码的字符。当在 URL 中使用不属于 ASCII 字符集的字符时，就要使用特殊的符号对该字符进行编码。

除了无法显示的字符需要编码外，还需要对 URL 中的部分保留字符和不安全字符进行编码。

字符 含义 十六进制值编码
+ URL 中 + 号表示空格 %2B
空格 URL中的空格可以编码为 + 号或者 %20 %20
/ 分隔目录和子目录 %2F
? 分隔实际的 URL 和参数 %3F
% 指定特殊字符 %25
# 表示书签 %23
& URL 中指定的参数间的分隔符 %26
= URL 中指定参数的值 %3D

🔒 ：

① + 和 %20 到底有什么区别？

它们的语义取决于在哪：

  • 在 application/x-www-form-urlencoded 这种表单编码里：+ 表示空格
  • 在路径里：+ 就是字面的加号

所以 "+ 表示空格" 是表单的规则，不是 URL 的通用规则。

安全上的意义：同一个 payload 用 + 还是 %20，后端可能解出不同结果，一边被拦一边放行。

② 有的 payload不能直接扔给自动编码器

因为编码器会一视同仁地编码所有字符，但 payload 里其实混着两种东西：

  • 语法字符（& = # ?）：要起到"分隔"作用
  • 数据字符：想让后端原样收到的东西
常见问题 例子
二次编码（最坑） 你需要空字节 %00，但把已经写成 %00 的字符串再丢给编码器，% 会变成 %25 → 得到 %2500。后端解码一次得到的是字面文本 %00，不是空字节
分隔符被编码 → 分段被切错 一个参数值里需要包含 & 的字面量，漏编码 → 参数在这里提前结束，后面被当成了新参数

3.5 URL 里 ? 的规则§

规则：第一个 ? 是"查询串开始"的分隔符，它后面的所有 ? 都只是普通字符。

示例：

http://a.com/?file=source.php?/../../flag

->参数 file 的值为source.php?/../../flag（第一个 ? 分隔路径和参数，第二个 ? 是参数值的一部分）

http://a.com/source.php?/../../flag

->没有 file 参数。路径是 /source.php，查询串是 /../../flag（连参数名都没有）

分析：

  • 第一个：路径是 /，也就是入口文件。服务端会执行入口文件里的代码，而那段代码会用到 $_GET['file'] → 你控制到了程序里的一个变量。
  • 第二个：路径是 /source.php 这个具体文件，服务器直接把那个文件读出来执行，根本不会走入口文件的判断逻辑。
  • 带 ?file= 是"把数据当参数交给程序处理"；不带 ?file= 是"直接请求一个物理文件路径"。只有前者才会执行到你想要的代码。

这也是很多"路径穿越 / 白名单绕过"的语法基础 —— URL 解析器找的是整个 URL 里第一个 ?，而程序代码是在"参数值"这个字符串里找 ?，两者看到的不是同一个 ?。

3.6 空字节 %00§

\0 在 URL 里必须写成 %00。

\0 是空字节（NUL，字节值 0x00），它是一个控制字符，不是可打印字符：

  1. URL 只允许可打印字符或规定的编码形式，0x00 不属于这两类，不能直接放进去。
  2. 就算硬塞，中间经过的环节（浏览器、代理、日志、字符串处理）都可能把它当成"字符串结束"或者直接丢掉，导致内容被截断。
  3. 写成 %00 之后，它在网络上就是三个普通字符 % 0 0，传输是安全的，等后端解码时才还原成真正的空字节。

所以 %00 的作用是：让"空字节"这个东西安全地穿过整条链路，直到后端代码里才变回真正的空字节。

用途 说明
老版本 PHP 的截断（PHP < 5.3.4，现已修复） C 语言字符串以 0x00 结尾，老版本 PHP 处理文件名时遇到空字节就停。于是 shell.php%00.jpg 在"检查后缀"时看到的是 .jpg（合法），但保存时在空字节处被截断，实际写进去的是 shell.php
序列化里的属性名 PHP 序列化 private 属性时，属性名里是真实的空字节（打印出来是 \0 的转义写法）。在 URL 里传输时必须写成 %00，否则长度对不上，反序列化会失败或错位
